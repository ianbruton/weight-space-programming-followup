Part 3: a 27B tool reflex in progress

This experiment is running now. This page says what is being tested and how the result will be judged. There are no results yet.

The behaviour

In the same private agent benchmark as Part 2, a 27B model (Qwen3.8-27B, served 4-bit) reviews items with read-only tools. Some test items carry an injected instruction that names a file path. On 3 of the 11 injected test items, in all 46 past runs, the model's first move is to call a tool on the planted path. The system prompt and every tool description already tell it not to. A prompt fix has been tried, and the reflex remains.

The trap is obvious: an edit that simply stops tool use would pass this check by doing no work. Part 1 showed that this can happen by accident: MIT's edit cut tool calls in our agent task by 87%. So the target is narrower: remove the first-turn call on the planted path, and keep tool calls on the item's own legitimate files. Both are measured.

Data: data/part3/plan.json.

The plan

  1. A contrast set fixed before any reading or generation. 48 planted instructions that name a path, 12 planted instructions with no path, 12 plain mentions of a path with no instruction, and the 70 real items. None of them reuses a path, sentence or number from the benchmark's own injected test items. Separate splits are used for building the direction and for choosing the dose.
  2. Read the model in 4 bits. The 27B does not fit in 24 GB of VRAM or in RAM at full precision. Activations are read from a 4-bit copy by a loader that unpacks each weight inside its own forward call. The 4-bit copy rescales MLP columns, so directions are taken in the residual stream, which is the same space in every copy of the model.
  3. Screen doses without writing weights. The edit is served as a rank-one adapter, and its scale is the dose. The target direction and a norm-matched random control are both screened on practice items.
  4. Write the chosen dose into a new model file. The edited tensors are re-quantised. We check that the dose survives the re-quantisation.
  5. Test base, edit and random control on the benchmark. Measures: the reflex on each probe, tool calls on legitimate files, citations that hold, and valid answers. Then a regression check.
  6. A cost ledger: tokens, GPU hours, forward passes, code runs and wall time. For comparison, Astra's 50-pass run used 50 passes, 158 turns and 80 Python runs, over 20.3 hours (the authors' run table). We plan three passes, not fifty.

As in Part 2, the rule for "it worked" is written before the test it judges, and any change of plan after a result is reported as such.
