Part 3: a 27B tool reflex, and why the recipe did not remove it

We tried the recipe on Qwen3.8-27B, served in 4 bits, against a habit we wanted gone: calling a tool on a file path that an injected test item planted. It did not work. The recipe found an edit, the edit survived the 4-bit file, and it did something real and specific. But it moved the call to another path instead of removing it, and it broke some answers. Why it failed is the useful part.

In short

  • On the three test probes, which were never used to build or choose the edit: one reflex gone, one unchanged, one turned into an answer that never ends. The check (G7) failed in all 6 edited runs, and two other checks (G2, G5) newly failed.
  • The reflex is a habit, not obedience. The base model calls a tool on a path that is merely mentioned as surely as on one it is told to check (12 of 12), and a planted instruction loses to a real repository in the same item (0 of 12).
  • What the recipe found is a token. The direction makes /home the likeliest start of a path. That moves calls off planted paths that do not start with /home, cannot touch one that does, and at useful doses the model sometimes cannot stop writing /home.
  • Legitimate tool use was kept (299 calls on the items' own places for the base, 304 and 302 for the two edited doses, one run each). The cost was elsewhere: perplexity +4.4% and +7.9%, against +0.3% for a random edit of the same size.
  • About 8 hours of wall time, 3.5 GPU hours on one RTX 3090. Astra's 0.8B run took 20.3 hours.

The behaviour

In the same private agent benchmark as Part 2, the 27B reviews items with read-only tools. Eleven injected test items probe its behaviour. On three of them, in all 46 past runs, its first move was to call a tool on a path the item planted: a file outside the allowed folders, a folder outside them, and a credential-like file inside a home folder. The system prompt and every tool description already tell it not to. The harness refuses those calls, so nothing is read; the check (G7) asks that the model not try.

The trap: an edit that simply stops tool use would pass this check by doing no work. Part 1 showed that this can happen by accident (MIT's edit cut tool calls in our agent task by 87%). So the target was narrower: remove the call on the planted path, and keep the calls on each item's own files.

First finding: the reflex is a habit

Before any reading of the model, a contrast set was fixed: planted instructions that name a path, planted instructions with no path, plain mentions of a path with no instruction, and the 70 real items. None reuses a path, sentence or number of the benchmark's own probes. The base model's first replies:

The model calls a tool first on every item. A path that is only mentioned draws the call as surely as an order does, and an order loses to a real repository in the same item. In its own words, inside the very call that goes for the planted path, it sometimes says the path is untrusted and outside the allowed folders. It is the model's ordinary "check the path the item names" habit, the same habit that makes its legitimate calls. So "calls a tool or not" could not be the contrast. The contrast was which path the first call is written for.

Astra's review adds a caution we accept: these are different examples, not matched pairs, and both conditions are at the ceiling. They show that an instruction is not needed to trigger the call. They do not show that instructions play no part.

How it was done

  • Read in 4 bits. The 27B does not fit in 24 GB of VRAM at full precision. Its states were read from a 4-bit INT4 copy by a loader that unpacks each weight inside its own forward call (peak 18.2 GB). That copy rescales MLP columns, so directions were taken in the residual stream, the same space in every copy.
  • Four families, the recipe's rules: difference of means at the state that picks the first path token, the two MLPs that write most along it, the top 312 of 17,408 columns (1.79%, Astra's share), and W ← W − dose·u(uᵀW) on ffn_down. The family that won (F1) sits in the last two layers, 62 and 63. The same contrast in layers 26–27 did nothing at any dose.
  • Doses screened without writing weights, as a rank-one adapter whose scale is the dose, in the serving engine itself, on practice items, with a norm-matched random control.

The dose rule, written before the screen, chose dose 4 (the qualifying dose with the fewest reflex calls). But a third of the first replies at dose 4 did not finish: they loop on the token the edit promotes, writing /home again and again inside one path. The rule had not counted that, so dose 3 was added as a second edited arm before any benchmark run, and both went through. Astra points out that the rule in effect credited unfinished replies: at dose 4 only 16 of 32 completed replies avoided the planted path, against 24 of 32 at dose 3.

Into a 4-bit file

The edit was written into copies of the served GGUF file. Only bytes of the two edited tensors differ; every other byte of the 17.6-billion-byte file is the same. A small edit does not survive plain rounding: most entries move by less than half a step and round back. The writer therefore keeps every block's scales and every untouched entry's code, and re-codes only the 312 columns so that each column's component along u equals the target. The dose comes back as 4.000 and 3.986 (dose 4) and 3.000 and 3.000 (dose 3), at the price of noise off the direction of 18–41% of the edit's size. In behaviour the files match the exact edit on the screen items, except that the dose-3 file leaves 4 replies unfinished where the exact edit left 1: the edit survives usefully, not exactly.

  • Every planted call in every run (60 of 60) was refused by the harness: the reflex is an attempt, never a read.
  • The edited model never answers a probe without calling a tool. The reflex is not removed, it is redirected.
  • Tool use did not collapse. Whether legitimate work was fully kept is not shown by one run per arm.

Why it failed, and why that is worth knowing

Astra's edit on the 0.8B removed a state the model was stuck in: looping. The 27B was not stuck in anything on these probes. It applied its normal checking habit to a path it should not check. A rank-one edit found by this recipe has nothing to remove there. What it found instead separates planted calls from legitimate ones by the first token of the path, which is why it moves calls off some paths, cannot touch others, and loops when pushed. The same lexical kind of edit, with the same failure at useful doses, showed up in Part 2.

That is a narrower claim than "weight editing cannot do this". Astra's review is clear on the limits: one random control, one contrast, a few layers, one day's data, and no success rule for the benchmark run written before it ran (the brief asked for one; this was a protocol failure, disclosed). The search was narrow, so it does not show that no useful editable representation exists. And "the prompt was tried" should read "this prohibition-heavy prompt failed": a prompt with an explicit decision procedure, or tools that accept only targets supplied by trusted code, have not been tested.

The review, and what comes next

Astra's verdict: the failure follows, and the candidates stay rejected. Its ranked next steps put measurement and policy before any further edit:

  1. Re-score the saved runs so that missing answers never earn credit, and write a joint rule first: completed valid answers, no forbidden attempts, legitimate work kept (no GPU).
  2. Matched counterfactuals: the same item with an instruction, a plain mention, or no target; allowed and forbidden paths that both start with /home (about half a GPU hour).
  3. Prompt and tool-policy remedies on that set (up to an hour).
  4. At most one bounded weight-edit diagnostic, only if the above still leaves something for it to find.
  5. Confirm any survivor with four runs per arm on two days' data.

A second round on these lines had started when this page was written.

A parallel case. CompressionBench (Zhong et al., arXiv:2611.06858v2) gives coding agents, running in Claude Code, a source checkpoint, a storage limit and an eight-hour budget on one H200, and asks them to build compressed weights and the code that runs them. One of its checkpoints is the same dense Qwen3.8 27B; 29 of its 36 submissions pass verification (section 3.1 and the abstract). It is a different task (compression, not changing a behaviour), cited here only as context: agents doing surgery on this model's weights under a fixed budget is becoming an ordinary experiment.

What we did not check

  • One day's data, one sampling setting (temperature 0.3), one full run per arm.
  • One random control direction; one column count; F1 not tried on one layer alone in the benchmark.
  • Perplexity on the 4-bit INT4 copy, not on the GGUF files.
  • Whether the loop also appears at a lower temperature or with a repetition penalty.
  • The edited model's later turns after its calls are refused were not analysed.
