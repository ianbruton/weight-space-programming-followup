Part 2: our own 4B citation edit

We used Astra's recipe on Qwen3.5-4B for a failure it really has: citations that point to the wrong place. The recipe transferred mechanically. One direction, two layers and the lowest dose raised the share of citations that hold by about 3.5 points, and it beat a random direction of the same size. The statistics need careful reading. So does what the edit actually is. On a second day's data the gain did not reach the items that were new that day, and a screen of 30 variants found nothing better than the first edit.

Reviewed by GPT-6 Astra (11 November). Astra recomputed every headline figure and re-checked all 3,276 citations of the twelve fresh runs, and found no discrepancies. Its verdict: a credible, modest improvement on this data; the declared success rule remains unmet; general improvement without regressions is not established. Fable agreed with all fifteen points. The corrections are applied on this page:

  • The intervals below resample items, with each arm's runs pooled. They leave out run-to-run variation. With the runs resampled too, edited − base is about 0 to +7.5 points (held-out −1.3 to +11.7). The gain is at the edge of zero once run-to-run variation is counted.
  • The held-out items were not used to fit the direction or to choose the family and the dose, but they were used earlier, in an exploratory survey. They are not untouched test data.
  • The control is one random edit, repeated over four seeds. The edit beat this control; the control itself was not distinguishable from the base (−1.2, −3.6 to +1.0).
  • "Held" means the quote is found where the citation says it is. Whether the quote supports the decision was not graded.
  • We did not find a "this citation will miss" direction with our probes. That does not show none exists.

What happened next is in Round 2: a second day's data, a tool-calling check, and a screen of variants with five random controls.

Re-scored on 12 November: when the same strict citation resolver scores both arms, the edit's lead over the base falls from +3.5 to +0.5 points (−1.1 to +2.5); see Scoring with a resolver.

In short

  • Citations that hold: base 89.7%, random control 88.4%, edited 93.1% (four runs per arm). Edited − base +3.5 points, 95% interval +1.1 to +6.2. About a third of the misses go.
  • The test we planned was two runs per arm. By the rule we wrote before running it, the result was "not shown". We then declared two more runs per arm, fixed their number, and ran them. The four-run result above comes from that extension, decided after we saw the first.
  • The edit does not make the model pass the whole benchmark more often: 2 of 4 runs, the same as the base.
  • It is not a "be careful" switch. It is a small re-weighting of words in the last layers; a later screen found that one layer (31) carries all of it. Higher doses produce answers that never end.
  • On a second day's data the edit held no more citations than the base on the 18 items that were new that day (−1.2 points). It did not raise tool-calling errors or perplexity.
  • Most of the gain was wrong paths that code can repair: with the same resolver on both arms, edited − base is +0.5 points (−1.1 to +2.5) on the first day and −1.9 (−7.4 to +2.5) on the second, a descriptive reading of reused runs that measures model plus repair, not the model unaided.

Why a different target

We first checked whether the 4B loops the way the 0.8B does. Under the post's settings (C1), on 128 practice problems, only 3 answers (2.3%) reached the 32,768-token cap, and 122 of 128 (95.3%) were correct. The 0.8B under the same settings had 85 of 96 at the cap. Astra's edit would have almost nothing to fix on the 4B.

Data: data/part2/base_4b_math_practice.json.

So we picked a failure the 4B does have, in a private agent benchmark.

The benchmark (private) and the failure

A review agent reads 70 items, plus 11 injected test items. It may call read-only tools, and for each item it returns a JSON decision with a list of evidence. Each piece of evidence is a citation: a ref, which is a path into the item's JSON (such as text), and a quote. A checker looks up the path. The citation holds if the quoted words are there. Seven run-level checks (G1–G7) decide whether a run passes. One of them (G5) is about citations.

From two earlier runs of the base 4B we took every citation of an item: 583 citations in 139 final answers. 492 cite the item: 415 hold and 77 do not. Most misses are of one kind. In 67 of the 79 misses the quote is right and it is in the item, but the path points elsewhere (for example facts[0].text where the sentence sits in text). The 4B's misses are wrong paths, not badly copied quotes.

Data: data/part2/contrast_set_and_survey.json.

Before reading any internal state, we split the items: an item is held out if sha256(key) mod 5 < 2. That gave 32 held-out items and 38 practice items. Directions were built on practice items only.

Is there a "this citation will miss" direction?

We did not find one with these probes. We read the base model's hidden states over every citation and built difference-of-means directions on practice items. Then we measured how well each separates misses from hits on held-out items (AUC; 0.5 is chance):

Where the path is decided, nothing separates the two. At the quote, the separation is already there at layer 0 (0.97), before any computation. That is the words themselves: misses mostly quote a prose sentence, and held citations mostly quote field values such as paths and numbers. The model is not unsure when it misses, either. At the fork, it gives the wrong path's token a median log-probability of −0.16 and the right one −2.6. These are confident errors about the JSON layout.

The recipe, applied anyway

A direct test was cheap, so we built four edit families with Astra's rules:

  • direction: a per-layer difference of means (misses minus held citations) on practice items;
  • layers: the MLPs that write most of that contrast;
  • columns: the top 165 by (write strength along u) × (activation contrast). That is the same 1.79% of the MLP width that Astra's 64 columns were on the 0.8B;
  • edit: W ← W0 − dose·u(uᵀW0) on those columns of mlp.down_proj;
  • control: a random unit direction orthogonal to every u, on the same columns, scaled so the weights change by the same amount (Frobenius norm).

We wrote a rule for choosing the family before running the screen. The screen reads the practice answers teacher-forced. At each fork it measures S, the change in log p(right path token) − log p(wrong path token). Family F1 (the tokens from the path to the end of the citation, matched inside each answer, layers 29 and 31) passed the rule and won. Its random control moved S the wrong way:

What F1's direction is. Read through the output layer, its "miss" side is prose words and the end-of-answer token (" day", " last", " not", " one", <|im_end|>). Its "held" side is JSON punctuation and pieces of field names. It is a lexical direction, as the survey warned. At dose 1 it changes the two tensors by 0.70% and 0.93% (MIT's edit changed its two by 8–11%).

The full test, with a random control

All 70 items, the same benchmark and settings as the earlier runs. Fresh base runs ran in the same jobs as the edits. Before any of these runs we wrote the rule for "it worked":

  1. every edited run holds a larger share than every fresh base run and every control run;
  2. on the held-out items, edited − base and edited − control are positive, with 95% intervals above zero (bootstrap over items, 10,000 draws);
  3. the edited runs are no worse than the base on valid answers, and pass the citation check G5.

  • The extension runs on their own show the same sign, with a smaller gain over the base: +2.4 points (−0.9 to +6.1). Against the control: +4.6 (+0.9 to +8.5). On their own, they do not separate the edit from the base.
  • Every one of the four edited runs (92.4–94.4%) is above every fresh base run (87.8–90.7%) and every control run (86.5–90.6%).
  • Misses fell by about a third: 113 of 1,092 citations (base), 130 of 1,121 (control), 73 of 1,063 (edited). The clearest single change is that a bare facts path nearly disappears.
  • The whole benchmark (checks G1–G6): the edited model passed in 2 of 4 runs, the fresh base in 2 of 4, the control in 1 of 4. Both edited failures were the same answer running to the cap. How we read it. The success rule we wrote before the test was not met, neither in the planned test nor after an extension decided after seeing it. What the twelve runs support is an exploratory estimate: about 3.5 points, a third of the misses, against a base that holds about 90%. With run-to-run variation counted, its interval reaches zero. It beat one random direction of the same size. And the edit does not make the 4B pass the benchmark reliably. Round 2 (below) tested it on a second day's data.

What the edit is, and what it is not

It is not a "quote exactly" or "be careful" direction; we did not find one in the 4B's states for this failure. It is a small lexical re-weighting in the last MLPs (165 columns, under 1% of each tensor's norm). For a quote of the item's sentence, it makes the 4B write paths that hold, most clearly text instead of a bare facts. It is not a blind push towards text: where text would be the wrong path, the edited model holds 95.1% of citations against the base's 93.4% (+1.7, −0.4 to +4.2). Read through the output layer, the end-of-answer token sits on the side the edit removes, which is consistent with answers that stop ending at higher doses; that mechanism was not isolated.

Data: data/part2/round2.json.

Round 2: the review, a screen of variants, and a replication

After the review, Fable ran one improvement round with its rules written first, and a separate replication with its own rules ran beside it.

More measures on the same twelve runs

  • Clean answers (valid, and every citation holds): base 72.1%, edited 79.3%, control 70.0% of 280. Edited − base +7.1 points (0.0 to +14.3; −2.5 to +16.1 with runs resampled).
  • Coverage: citations per valid answer fell 2.1% (−9.5% to +6.0%). So the gain is not bought by citing visibly less, but a loss of up to a tenth of the citations is not excluded.
  • With the 22 kinds of item as the unit instead of the 70 items: edited − base +3.5 (+0.5 to +6.6). The edited model does better in 10 kinds, worse in 6, the same in 6. The effect is not carried by one kind, but all of this is one day's layouts.

This time there were five independently drawn random controls. The rule, written first, sent a variant to the real benchmark only if it predicted about twice the first edit's gain.

  • Layer 31 carries all of it. Layer 29 alone is inside the controls' range. In effect the edit is a one-layer change of 0.93% of one tensor.
  • The first edit's fork score is nine times the largest of the five controls'.
  • The probability of the end-of-answer token after a finished answer does not move under any variant. So the edit does not touch stopping at the natural end of an answer; the answers that never ended were lists that kept growing, which this measure does not see.

Scoring with a resolver (12 November)

Most of what the edit fixed was one kind of miss: the right quote at the wrong path. Code can repair that kind of miss after the model has answered. So we asked: if the same repair is applied to the base and to the edited model, how much of the edit's lead is left? We re-scored every saved 4B run with a strict resolver. This needed no GPU and no new model runs, and the resolver's rules were written down before it existed. Below, 25 October is the first day's data and 9 November the second's.

What a strict resolver does.

  • A citation the checker accepts stays accepted. It never takes a held citation away.
  • A rejected citation of the item is looked for only inside that item, as the model saw it. If the quote stands in exactly one place, the citation is moved there and holds. If it stands in two or more places, it is ambiguous and stays rejected: the resolver does not choose. If it stands nowhere, it stays rejected.
  • A rejected tool citation is looked for only in the tool result its reference names. There is no search across results, and no crossing from a tool result to the item or back.

Checks: a replay of the checker matched the recorded verdict of every answer in all 36 runs (0 mismatches), and the original column below reproduces every published total. GPT-6 Astra replayed all 36 runs (1,858 answers, 6,921 citations) and reproduced the headline numbers.

Why the lead shrinks

The base has more mistakes that the resolver can repair: of its rejected citations on 25 October, 67 are a quote that stands in exactly one other place in the item, against 34 for the edited model (on 9 November, 36 against 15). After the repair the two are left with about as many rejected citations: 46 for the base and 39 for the edited model, over four runs each. The edit's gain was mostly in the kind of miss that code can repair, and what the resolver leaves is not where the edit helps.

  • Ambiguous: the item states the same words in two or more fields, most often two fields that repeat each other (a short number can also stand inside many longer values), so the strict rule refuses to choose.
  • Quote not in the item: mostly reformatted quotes (a number quoted together with its field name, list entries joined with commas), and quotes taken from a tool result but labelled as the item's.
  • Tool citations: real misquotes of a tool result, or references the checker cannot match to any result. No tool citation was repaired in any arm.
  • Against the random control a small edge remains on 25 October (+2.4, +0.2 to +4.9). The control itself falls below the base after the repair (−1.9, −3.7 to +0.1), because it has more misses that cannot be repaired. That is not a gain of the edit over the base.

Corrections after Astra's review

Astra found a fault in the resolver's search and some overstatements. The counts on this page are the corrected ones; no score moved.

  • The search stopped early where a field's escaped text hid a match below it. Searching every field moved 31 citations from "quote not in the item" to "ambiguous". None of them changed from rejected to held.
  • Held citations that point at a whole list or object instead of a field are about 2% (25 October: 25 of 979 for the base, 21 of 990 for the edited model), not the quarter first reported.
  • Tools without a path argument can be cited, by the bare tool name, which the resolver's first report denied. More generally, the checker identifies a tool result by its name and path only, so one held tool citation can cover several different calls (4–6 held citations an arm on 25 October). The resolver keeps every citation the checker accepts, so it inherits this limit.

What this does and does not show

  • It is descriptive, on reused data, not a confirmation. Every run here had been read and used for choices before. These items have now also been inspected under the resolver, so new seeds on the same items would not make an untouched test of a resolver-informed next round.
  • It measures model plus repair, a different task. It does not erase the edit's gain on producing correct references unaided: the +3.5 points on 25 October stand as an exploratory gain under the original checker.
  • It does not show that the edit has no effect, that the two arms are equivalent, or that the prompt paragraph is better. The paragraph's +4.6 is a point estimate, and its interval crosses zero.
  • The arms produced different citations, so "67 against 34" is a total. It is not evidence that the edit fixed particular mistakes that the base made.
  • The intervals hold the recorded runs fixed. With each arm's runs resampled too (decided after the fact), the resolved edited − base is −2.3 to +4.2 on 25 October and −9.0 to +3.4 on 9 November. Block 1 has one run a cell, so its intervals cannot include run-to-run variation.
  • The resolver checks where a quote stands, not whether it supports the decision. Its corrected rules have not been reviewed again.
  • Not concluded: whether to drop the citation edit. That waits for blocks 2 and 3 of the prompt test. For practical value, the comparison that matters next is what the edit adds on top of the base with the prompt paragraph and the resolver, on complete answers and on how much is cited, against an effect size fixed in advance.

Cost, against Astra's

The editor here was a Claude agent (Fable 5.2 in Claude Code) with its own scripts. It read the model's internals directly. Astra had a fixed budget of forward passes and no GPU in its kernel. So the two are not the same task. For scale: our 4B work took about 4.7 GPU hours in five jobs, and 12.75 hours of wall clock from the first entry to the last. Most of the GPU time went to benchmark runs, not to finding the edit. Astra's 50-pass run took 20.3 hours.

Data: data/part2/cost.json; Astra's run: the authors' run table.

What we did not check

  • One prompt set and one sampling setting (temperature 0.3). In the full tests, one random control direction (the screen in Round 2 had five).
  • The direction came from 14 practice answers in two runs.
  • Doses 2–6 went through the 24-item screen only. F2–F4 and the Round 2 variants went through the teacher-forced screen only.
  • The edit was served in bf16 from safetensors. No quantised copy was checked.
